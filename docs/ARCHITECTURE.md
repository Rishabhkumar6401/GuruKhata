# Architecture & tech stack

Principle: **Rohan's existing stack (plain JS + Node + SQL), smallest possible moving parts, everything replaceable later.** This is a product, not a résumé piece — boring choices win.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Frontend | React + Vite, plain JS, mobile-only layout | ~7 screens; Vite PWA plugin gives manifest + service worker cheaply |
| PWA → Store | TWA wrapper (Bubblewrap) in Phase 4 | same codebase becomes the Play Store app |
| API | Node.js + Express (plain JS) on **AWS Lambda** (via `serverless-http`, Lambda Function URL — no API Gateway needed) | always-free 1M req/mo, no cold-sleep like Render free, no non-commercial clause like Vercel Hobby |
| DB | **Neon Postgres** (free 0.5 GB) | real SQL, branching for dev; 0.5 GB ≈ hundreds of thousands of student/due rows — years of headroom |
| Auth | Google Sign-In (OAuth) | free, zero OTP cost, every Android tutor has a Google account; phone-OTP login is a paid trap (SMS costs) — avoid |
| Scheduled jobs | Lambda + EventBridge cron (free tier) | monthly dues generation on the 1st; daily "dues today" push at 8 am |
| Push | Web Push (VAPID) — `web-push` npm | free, serverless-friendly, works on Android Chrome PWA/TWA (iOS irrelevant for persona) |
| Receipts | client-side canvas → PNG | zero server cost, works offline |
| WhatsApp v1 | `wa.me/<phone>?text=<prefilled>` deep links | ₹0, no Meta approval, sends from teacher's own number (more parent trust than any business bot) |
| WhatsApp paid tier (Phase 4) | Meta WhatsApp Cloud API | utility templates ~₹0.12/msg — only for paying users, priced into the plan |
| AI (Phase 4, paid tier) | Claude Haiku API for drafting reminders/progress notes | cheap per call; free tier uses static smart templates so free users cost ₹0 |
| Payments (Phase 4) | Razorpay subscriptions (INR, domestic) | ~2% per txn, no setup fee; no MoR needed for India-only sales |
| Analytics | Cloudflare Web Analytics | free, no cookie banner needed |

## Data model (v1)

```sql
tutors      (id, google_sub, name, phone, upi_id, language_pref, tone_pref,
             role,                               -- 'tutor' | 'admin' (Rohan's google_sub seeded admin)
             plan, plan_expires_at,              -- 'free' | 'paid'   (Phase 4)
             created_at, last_active_at)
students    (id, tutor_id FK, name, parent_name, parent_phone, subject,
             monthly_fee, due_day, active, created_at)
dues        (id, student_id FK, month,            -- '2026-10'
             amount, status,                      -- due | paid | waived
             paid_at, receipt_no, UNIQUE(student_id, month))
reminders   (id, due_id FK, sent_at, channel,     -- wa_link | push | api
             template_used)
push_subs   (id, tutor_id FK, endpoint, keys_json, created_at)
```

Notes:
- `dues` rows are generated by the monthly cron (idempotent: `INSERT ... ON CONFLICT DO NOTHING` — a re-run must never double-bill)
- receipt_no = simple per-tutor sequence (`TUT-2026-0042`) — tutors like official-looking numbers
- no batches/classes table in v1 — `subject` string is enough for 10–50 students; batch segment (25–60 students) gets a real `batches` table in Phase 2.1 (students.batch_id)

## Backoffice / super-admin (added 2026-10-02 on Rohan's call)
NOT a separate system — a protected area of the same API + a few plain pages:
- `role='admin'` on tutors; admin routes behind `requireAdmin` middleware (role check on JWT)
- `/admin` pages (desktop OK, it's only for us): tutor list w/ student counts + last_active, signups/day, dues created vs paid, reminders sent, plan status (Phase 4), read-only "view as tutor" for support
- Audit rule: every admin write (plan change, deactivate) logged to `admin_log(id, admin_id, action, target, at)`
- Scale trigger: separate admin app only if a second staff member ever exists

## Key flows

**Monthly cycle (the whole product):**
1. Cron, 1st of month → insert `dues` for every active student
2. Cron, daily 8 am → tutors with dues where `due_day = today` get one push: "5 students' fees due today"
3. Tutor opens app → Overdue list → taps student → app builds `wa.me` link with template (name, month, amount, UPI ID interpolated) → WhatsApp opens → tutor taps Send
4. Money arrives in tutor's UPI directly (we NEVER touch the money — no payment-aggregator licensing, no liability)
5. Tutor taps "Paid" → due updated, receipt PNG rendered → share sheet → parent gets receipt

**Security/simplicity notes:**
- We never store parents' data beyond name+phone; no student PII beyond name (keep it minimal — these are minors' names, treat with care)
- JWT sessions (httpOnly) after Google sign-in; every query scoped `WHERE tutor_id = ?` (multi-tenant rule #1 — Rohan knows the cost of missing this from work)
- Rate-limit the API by tutor; receipts and reminders work offline-first where possible

## What we deliberately did NOT choose (and why)
- **Supabase all-in-one:** tempting, but Edge Functions are Deno/TS and auth lock-in is real; Neon+Lambda keeps us in plain Node
- **Render/Railway/Fly free tiers:** sleep/cold-start or credit-expiry problems for a daily-use app
- **Vercel Hobby:** ToS prohibits commercial use — disqualifying for a paid product
- **React Native / native Android:** second stack, slower iteration; TWA covers the Play Store need
- **Phone-OTP login:** every SMS costs money; Google Sign-In is free and universal on Android
